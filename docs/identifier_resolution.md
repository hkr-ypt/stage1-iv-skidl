# Identifier resolution report

Every symbol name, footprint name and pin number in this project is now **read
from an installed library file** by `tools/resolve_kicad_libs.py`. Nothing below
is asserted from memory; every row carries the file and line the value came
from, and every read is reproducible with the committed tooling.

## 0. What the values were read from

| | |
|---|---|
| symbol library | `/usr/share/kicad/symbols` — kicad-symbols **9.0.9.1**, commit `ad36cd14bcd1b1cd0484f629ccdd3481366f74f3` |
| footprint library | `/usr/share/kicad/footprints` — kicad-footprints **9.0.9.1**, commit `2b941bf1d97862be429793b46fd52a5add09a2fc` |

Reproduce any single value:

```bash
python3 tools/resolve_kicad_libs.py --paths --json
python3 tools/resolve_kicad_libs.py --symbol    Analog_DAC:DAC8552
python3 tools/resolve_kicad_libs.py --footprint Connector_USB:USB_C_Receptacle_GCT_USB4085
python3 tools/resolve_kicad_libs.py --find-symbol 'REF502*'
```

## 2. Pin numbers

### 2a. Placeholder pin numbers are gone

`libraries/custom_symbols.py` no longer writes pin numbers at all. Each factory
names a `lib_id` and the pins — numbers, names, electrical types — are read from
the symbol file at build time. A `lib_id` that does not resolve raises
`SymbolResolutionError` and the build stops.

| Ref | before | after |
|---|---|---|
| U9 STM32F411RETx | 25 sequential placeholder pins (`1…25`) on a 64-pad LQFP | all **64** official pins, `MCU_ST_STM32F4.kicad_sym:332580` |
| U8 ADS1256 | 22 sequential placeholder pins on a 28-pad package | all **28** official pins, `libraries/stage1_iv.kicad_sym:15` |

`Pins_Verified == "PLACEHOLDER-REMAP"` no longer exists anywhere;
`validation/footprint_check.py` hard-fails if it returns.

### 2b. Pin numbers that were wrong and were **not** in the original brief

The audit's number→name comparison against the official symbols found three
further mis-numbered parts. All three had "correct-looking" pin *sets*, so no
existing check could see them:

| Ref | pin | design said | official symbol says |
|---|---|---|---|
| U4 DAC8552 | 2 | `VOUTA` | `V_{REF}` |
| | 4 | `VREF` | `V_{OUT}A` |
| | 5 | `GND` | `~{SYNC}` |
| | 6 | `SYNC` | `SCLK` |
| | 7 | `SCLK` | `D_{IN}` |
| | 8 | `DIN` | `GND` |
| U2 REF5025 | 5 | `VOUT` | `Trim/NR` |
| | 6 | `TRIM/NR` | `Vout` |
| U5 OPA548T | 1…7 | `E/S, V-, -IN, +IN, ILIM, V+, OUT` | `+, -, CS, V-, V+, ~, E/S` |

Every one of these would have shorted a supply or swapped a reference for an
output on the fabricated board. They are fixed by construction now — the numbers
come from the library, so the design cannot disagree with it.

### 2c. Alias layer

Where the official pin name differs from the design's functional name, the SKiDL
pin carries the design name and the symbol's own name is kept as an alias, so
both spellings address the pin and the pin *number* is always the library's.
The complete map is `ALIAS_DOCUMENTATION` in `libraries/custom_symbols.py`:

| factory / symbol | design name → pin | official name |
|---|---|---|
| `C_POL` / `Device:C_Polarized` | `+` → 1, `-` → 2 | `~`, `~` (the `+` glyph is drawn on the pin-1 side) |
| `USB_C_Receptacle` / `…USB2.0_16P` | `DP` → A6+B6, `DM` → A7+B7 | `D+`, `D-` |
| `LD1117S33` | `VOUT` → 2, `VIN` → 3 | `VO`, `VI` |
| `REF5025` | `VIN`→2 `TEMP`→3 `TRIM/NR`→5 `VOUT`→6 `NC1`→1 `NC2`→7 `NC3`→8 | `Vin Temp Trim/NR Vout DNC NC DNC` |
| `DAC8552` | `VDD`→1 `VREF`→2 `VOUTB`→3 `VOUTA`→4 `SYNC`→5 `DIN`→7 | `V_{DD} V_{REF} V_{OUT}B V_{OUT}A ~{SYNC} D_{IN}` |
| `OPA2277` | `OUTA`→1 `-INA`→2 `+INA`→3 `+INB`→5 `-INB`→6 `OUTB`→7 | `~ - + + - ~` |
| `OPA548` | `+IN`→1 `-IN`→2 `ILIM`→3 `OUT`→6 | `+ - CS ~` |
| `INA128P` | `RG1`→1 `-IN`→2 `+IN`→3 `REF`→5 `OUT`→6 `RG2`→8 | `Rg - + Ref ~ Rg` |
| `ADS1256` | `XTAL1`/`CLKIN` → 19, `SYNC`/`PDWN` → 14 *(additive aliases)* | `XTAL1/CLKIN`, `SYNC/PDWN` |
| `USBLC6_2SC6` | `IO1`→1 `IO2`→3 `IO2b`→4 `IO1b`→6 | `I/O1 I/O2 I/O2 I/O1` |
| `BananaJack` | `FORCE+`/`SENSE+`/`SENSE-`/`FORCE-` → 1 *(additive)* | `Pin_1` |
| `STM32F411RET6` | *(none — the official names are already the design's)* | |

**Deviation from the brief, stated plainly.** The plan asked for the official
name to stay as the pin's name with the design name added as an alias. Doing it
in that direction breaks the hard constraint that the eight existing assertions
pass *unchanged*, because they compare `pin.name` (`_has(n.VREF_2V5, "U4",
"VREF")` would fail against a pin named `V_{REF}`). The direction is therefore
inverted: design name primary, official name as alias. Both spellings resolve,
the official name is never lost, and the fabrication-critical value — the pin
number — always comes from the library.

## 3. USB-C modelling (P0-D)

| pad group | before | after |
|---|---|---|
| GND (A1, A12, B1, B12) | only A1 connected — 3 pads floating | all four on `DGND` |
| VBUS (A4, A9, B4, B9) | only A4 connected — 3 pads floating | all four on `VBUS` |
| D+ (A6, B6) | only A6 — worked in **one cable orientation only** | both tied to `USB_DP_CONN` |
| D- (A7, B7) | only A7 — same defect | both tied to `USB_DM_CONN` |
| SBU1/SBU2 (A8, B8) | not declared | explicit no-connect, allow-listed with a reason |
| shield | declared as pin `S1` | pad `S1` (4 shell tabs), tied to `DGND` |

**Correction to the brief.** The brief states the footprint's shield pads are
named `SH` and that the symbol's `S1` therefore emitted a node on a
non-existent pad. That is not what the installed footprint contains:
`USB_C_Receptacle_GCT_USB4085.kicad_mod` names all four shell pads **`S1`**
(lines 357, 365, 373, 381), and the `USB_C_Receptacle_USB2.0_16P` symbol names
pin `S1` `SHIELD`. The shield connection was therefore already landing on the
right pads. The genuine defects were the missing GND/VBUS pads and the
single-orientation data pair; those are fixed.

**Shield decision (stated, not accidental).** The shield is tied **directly** to
`DGND`, with no series RC or ferrite. (Correction: this paragraph used to say
the board is bus-powered. It is not: it is powered only from the bench supply
on J1, and VBUS is only sensed on PA0. The reasoning below does not depend on
it.) The board lives in one enclosure with a single USB-C cable to the host,
so there is no chassis-to-signal-ground
potential difference for an isolating network to manage; a direct tie is the
lowest-impedance return for cable-shield ESD and common-mode current and keeps
the shell from floating. The analog domain is unaffected: AGND reaches DGND only
through the R31 star point.

A new assertion, `a_usb_c_pads_fully_connected`, enforces all of this: four GND
pads on DGND, four VBUS pads on VBUS, both D+ pads on one net, both D- pads on
one net, shield netted.

## 6. How the KiCad-side numbers were obtained — and what could not be done

`kicad-cli sch erc` **does not exist in KiCad 7**, which is the newest version
installable in this environment (the KiCad PPA is blocked by the network egress
policy). **The KiCad ERC dialog was therefore never run, and no GUI session,
"Update PCB from Schematic", or ratsnest inspection was performed.** Anything
below that is described as measured was measured another way; nothing is
reported as a KiCad ERC result that did not come from a real tool.

What *was* run, and is reproducible:

* **`tools/kicad_roundtrip.py`** — hands `stage1_iv.kicad_sch` to
  `kicad-cli sch export netlist` (KiCad 7.0.11) and compares KiCad's own reading
  of the hierarchy against `stage1_iv.net`. Result: KiCad loads all nine sheets
  and produces **307 connections partitioned into exactly the same 66 nets**,
  with identical names after stripping KiCad's sheet-scope prefix. This is the
  strongest available substitute for opening the schematic by hand: KiCad's
  parser, not ours, read the files.
* The two ERC counts in §5a are computed by the same script from the live
  circuit against the installed libraries — they are exactly the conditions
  KiCad's *"Symbol not found in symbol library"* and *footprint link* checks
  test, evaluated on the same data KiCad would use. The before-column numbers
  come from running the identical script against commit `99aa6d4`.
* **`validation/footprint_check.py`** — the structural guard, wired into
  `main.py` so the build aborts on any failure.
* **`tools/test_guard_fails.sh`** — reintroduces five defects one at a time in a
  scratch copy and asserts both `footprint_check.py` and `main.py` exit
  non-zero. All five are caught.

Consequently, the following brief items are **not** delivered and are not
claimed: the KiCad ERC violation counts by type from the ERC dialog, and the

U9 and every AVDD/AGND/DVDD/DGND pad of U8 carries its rail net, which is what
"Update PCB from Schematic" would turn into a ratsnest.
